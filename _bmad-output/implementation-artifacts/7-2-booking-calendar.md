# Story 7.2: Vista calendario

Status: done

## Story

As a pilota,
I want vedere il calendario dei velivoli,
so that scelga un buco libero (FR-19).

## Acceptance Criteria

1. **Given** prenotazioni esistenti, **When** apro il calendario in vista giorno o settimana, **Then** vedo le colonne per velivolo con i blocchi prenotati (nome prenotante visibile agli autenticati) e posso navigare tra le date; la vista è usabile da mobile.

## Contesto e decisioni di design (vincolanti)

- **Il calendario vive DENTRO `/dashboard/bookings`** (la pagina di 7.1), come sezione principale SUBITO dopo l'header: ordine pagina = header → **calendario** → form "Nuova prenotazione" (invariato, solo `canCreate`) → "Prossime prenotazioni" (invariata). Nessuna route nuova: UJ-1 è "guardo il calendario, scelgo il buco, prenoto" — tutto su una pagina.
- **Stato vista SOLO via query param** (pagina server-rendered, zero stato client per la navigazione): `view=day|week` (default `day`), `date=YYYY-MM-DD` (default: oggi Europe/Rome), sanitizzati col pattern `sanitizeScope` di 6.4 (valori invalidi → default, MAI errore). **Lezione 6.4 M1 (crosstalk href)**: `pageHref` della lista DEVE preservare `view`/`date`, e gli href del calendario (prev/oggi/next, toggle vista) DEVONO preservare `page` — un query-object di next-intl `Link` SOSTITUISCE l'intera query string.
- **Vista giorno** = colonne per velivolo (TUTTI i non archiviati via `listBookableAircraft`, inclusi `OUT_OF_SERVICE` con badge motivo — le loro prenotazioni pre-fermo esistono e si devono vedere), asse verticale ore **06:00–22:00 Europe/Rome**, blocchi posizionati in assoluto per wall-time (top/height % sui minuti da 06:00 su 960'). Blocco = orario inizio–fine + nome prenotante (+ istruttore se presente, stile secondario). Blocchi che sforano la finestra 06–22: clampati al bordo con indicatore (▲/▼ o simile), MAI nascosti — doc-comment. Vista settimana = griglia righe-giorni (lun–dom) × colonne-velivolo, celle con chip compatti `HH:MM–HH:MM Nome`; entrambe le viste soddisfano "colonne per velivolo".
- **Timezone: il giorno calendario è Europe/Rome** (`APP_TIMEZONE`), i dati restano istanti UTC (AD-8). NUOVO helper `src/lib/zoned-time.ts` (puro, unit-testato, NIENTE librerie nuove): `zonedMidnightUtc(dateOnly: string, timeZone: string): Date` (l'istante UTC della mezzanotte wall-clock di quel giorno in quella zona — algoritmo: parti da `Date.UTC(y, m-1, d)`, leggi il wall-clock che quell'istante produce nella zona via `Intl.DateTimeFormat` con `hourCycle: 'h23'`, correggi della differenza, ripeti la correzione UNA seconda volta per i giorni di cambio ora); `zonedWallTime(instant: Date, timeZone: string): { hour, minute }` per il posizionamento dei blocchi; `weekStartDateOnly(dateOnly: string): string` (lunedì ISO, aritmetica date-only pura). Range giorno = `[zonedMidnightUtc(d), zonedMidnightUtc(d+1))`; settimana = `[lunedì, lunedì+7)`. Test obbligatori su CET (+1, gennaio), CEST (+2, luglio) e transizioni DST 2026-03-29 / 2026-10-25. MAI `new Date('YYYY-MM-DD')` nudo per questi calcoli e MAI `date-only.ts` per posizionare istanti (quello è per `@db.Date`).
- **Data dal service, non paginata**: nuova `listCalendarBookings(actor, { from, to })` in `bookings.service.ts` — `authorize('self.read')` (qualunque autenticato, FR-19), `from`/`to` OBBLIGATORI, `to > from` → 422, **range massimo 8 giorni** → 422 (`ValidationError`, code `RANGE_TOO_WIDE`), predicato overlap-col-range semi-aperto IDENTICO a 7.1 (`startsAt < to AND endsAt > from`), ordine `startsAt asc, id asc`, `take: 1000` con doc-comment (bound di sicurezza, non paginazione: un calendario non si pagina). Riusa `BOOKING_SELECT`/`toListItem`. API gemella `GET /api/v1/bookings/calendar` (AD-1, parità Flutter): query schema Zod con refine range, registry tag `['Bookings']`, errorResponses 401,403,422.
- **Nav estesa a tutti gli autenticati**: `nav-items.ts` → voce `bookings` aggiunge `self.read` ai permessi (pattern flights 5.4 / expiries 6.2: la pagina decide cosa mostrare — l'allievo vede calendario e lista, NON il form perché `canCreate` resta sui permessi manage). **ATTENZIONE contratto 7.1**: `e2e/bookings.spec.ts` oggi asserisce che l'allievo NON vede la voce nav "Prenotazioni" — quel test VA AGGIORNATO (l'allievo ora la vede, apre la pagina, vede il calendario coi nomi, e NON vede il form né può POSTare — il 403 API resta). Stesso giro di 6.2 sul test nav di 6.1: aggiornamento atteso, dichiararlo, non "fixarlo" silenziosamente.
- **Nomi visibili a ogni autenticato** (FR-19 + assumption PRD §377-379): il calendario mostra nome prenotante e istruttore per TUTTI gli autenticati — nessun oscuramento per ruolo. Niente evidenziazione "mie prenotazioni" (non richiesta: non-goal dichiarato, eventualmente 7.3 quando arrivano le azioni own).
- **Mobile-usable (AC esplicito)**: entrambe le viste dentro contenitori `overflow-x-auto` con larghezza minima per colonna velivolo (`min-w`), MAI overflow orizzontale del body (convenzione tabelle esistente); controlli di navigazione (prev/oggi/next, toggle giorno/settimana) con touch target ≥44px; vista giorno default. Verifica interattiva Playwright MCP ANCHE a viewport 375×812 (obbligatoria prima degli e2e) + un test e2e con viewport mobile.

### Debug Log References

- `zonedMidnightUtc`'s double-correction algorithm was validated numerically BEFORE writing the doc-comment/tests (a scratch Node script computing `zonedMidnightUtc` for 2026-01-15/07-15/03-29/03-30/10-25/10-26 in Europe/Rome), to have ground truth independent of the implementation: CET midnight = `23:00Z` the previous day, CEST midnight = `22:00Z`, 2026-03-29's day = exactly 23h, 2026-10-25's day = exactly 25h — all confirmed, then encoded as `zoned-time.test.ts` assertions.
- Two small, necessary additions beyond Task 1's three named functions: `addDaysDateOnly` (date-only `+N days`, needed for the day view's `[date, date+1)` boundary and the week view's 7 date labels) and `todayDateOnlyInZone` (the `?date=` default, "oggi Europe/Rome" — the en-CA `Intl` locale trick for a guaranteed `YYYY-MM-DD` format). Both are pure, unit-tested, and documented in `zoned-time.ts` as intentional minimal extensions, not scope creep — the alternative (duplicating this arithmetic inline in `page.tsx`, twice) would be worse.
- Interactive Playwright MCP verification (desktop AND 375×812 mobile, per the mandatory pre-e2e check) caught TWO real bugs before the automated e2e run:
  1. A booking entirely before 06:00 (both `top` and `bottom` clamp to 0%) collapsed to the `MIN_BLOCK_HEIGHT_PERCENT` sliver — 3% (23px) was not tall enough to fit the clamp indicator + time + name without `overflow-hidden` visibly clipping the text. Fixed by raising it to 8% (~61px), verified clean afterward.
  2. The day view's aircraft-column header is a FIXED-height flex row (it must align exactly with the hours gutter's own fixed height) — a long `statusReason` on an OUT_OF_SERVICE badge wrapped to two lines and overflowed the fixed height, visually overlapping the hour grid below it. Fixed by truncating the badge to one line (`truncate` + `title` for the full text) and bumping the row height slightly (`h-11` → `h-12`) for breathing room. The week view's table-based header has no equivalent issue (table cells grow with content) — verified.
- Also verified interactively: href crosstalk preservation (lesson 6.4 M1) in BOTH directions — pushed the "Prossime prenotazioni" list past its first page (created extra bookings) and confirmed the calendar's prev/today/next/toggle links all carry `&page=2`; separately confirmed the list's own pagination links carry `&view=week` when the calendar isn't on its default day view. Also verified: the student role (no `bookings.manage.*`) sees the calendar with the pilot's name on it and no create form, and a direct `POST /api/v1/bookings` still 403s; DST-correct wall-clock display end-to-end (09:00Z real booking showing as 11:00 CEST on today's actual date, matching the season).
- **e2e stability finding (test-only, no application code affected)**: while running the full `bookings.spec.ts` suite, three PRE-EXISTING (7.1) UI-form tests started failing with the form's own "Campo obbligatorio" validation firing on submit, as if `Velivolo` had never been selected. Root-caused via a minimal repro spec (see below) to a genuine hydration race: `page.goto()` only waits for the `load` event, not for React to finish hydrating — and this page's DOM is now considerably larger (the calendar's hour grid × aircraft columns, plus however many rows "Prossime prenotazioni" has accumulated in a long-lived dev DB), so hydration can take long enough for Playwright's fast automated `selectOption()` to land BEFORE React attaches its handlers; when hydration then reconciles, it resets the native `<select>` back to its SSR'd `defaultValue`, silently discarding the interaction (confirmed with a throwaway repro: `selectOption` immediately after `goto()` left the select empty; the identical call after `page.waitForLoadState('networkidle')` set it correctly every time). Fixed with a new test helper, `gotoBookingsAndWaitForHydration`, used by the three affected pre-existing tests only (the tests that never interact with the create form — the calendar tests, the updated student-nav test — do not need it and were left on plain `page.goto`). This is a legitimate, narrow test-hardening fix; it does not touch `src/`.
- **DB-volume finding (session-specific, NOT a regression — flagged per Dev Notes/task instructions)**: after the hydration fix, the SAME three pre-existing tests still failed, now one step later — the freshly created booking's row wasn't visible on "Prossime prenotazioni" page 1. Root-caused via a direct `psql` count: this long, un-resettable session (extensive interactive Playwright MCP verification, PLUS several full/partial e2e re-runs while diagnosing the hydration race above) has accumulated 39 future bookings, only 8 of which are the far-future (`2031-03-10`, `FUTURE_DAY`) ones these three tests rely on; the other 31 are near-term (`2026-07`) bookings from this session's own testing, which sort BEFORE `2031` and fill all 20 slots of page 1. The exact same accumulation (this session created roughly a dozen extra `Aircraft` and `Person` rows via `bookings.spec.ts`'s own helpers, run repeatedly) also explains why several UNRELATED specs (`aircraft-management`, `aircraft-rates`, `aircraft-status-hours`, `flights`, `flight-reversal`, `package-consumption`, `people-management`) newly show list-pagination/hydration symptoms of the identical class documented in 7.1's own review (`people-management` sotto carico) — confirmed via `git diff --stat` that ZERO files touched by story 7.2 overlap with those specs' application code (aircraft/flights/people/packages are entirely untouched by this diff).
