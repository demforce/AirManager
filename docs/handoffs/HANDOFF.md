- **Regole utente**: ogni **epic ha la sua PR**; ogni **story ha i suoi commit** (story file → implementazione → review record/fix); a **epic finito**: `/handoff`, push, **STOP** — l'epic successivo parte in una NUOVA sessione.

## What Didn't Work

- **Dev server STALE su :3000 avvelena i run e2e** (`reuseExistingServer: !CI` in playwright.config): un server avviato a metà implementazione dal dev agent è sopravvissuto alla sua sessione e ha prodotto 2 fail "deterministici" FALSI su person-profiles (404 al posto di 403) che sembravano una regressione. LEZIONE OPERATIVA (ora nei story file): prima di ogni run e2e di gate, `curl localhost:3000` DEVE fallire; altrimenti `pkill -f "next dev"`.
- **F1 di 6.3 (unico mandatory dell'epic con 6.4 M1): assert e2e sui CONTATORI GLOBALI del job** → race coi test paralleli che creano anch'essi scadenze dovute (1 fail su 7 run). Regola: negli e2e asserire SOLO osservabili run-unique (mailbox del destinatario run-unique, contenuto del digest cercato per cognome run-unique), MAI risultati globali di un endpoint condiviso.
- Il dev agent di 6.4 NON può resettare il DB (il guard AI-consent di `prisma migrate reset` e il classifier dei permessi sul TRUNCATE di massa rifiutano correttamente): il suo gate e2e è girato su DB accumulato producendo 4 fail da VOLUME (righe oltre PAGE_SIZE/cap picker). Funziona: la sessione principale fa il reset (`DROP DATABASE ... WITH (FORCE)` via sudo postgres è permesso) PRIMA di lanciare dev/review, e il reviewer riceve il DB fresco.
- Il container si è riavviato 2 volte a metà epic (una a metà run e2e, una a metà review): i background task muoiono (Mailpit, dev server, workflow). Il workflow interrotto si riprende con `TaskStop` + `Workflow({scriptPath, resumeFromRunId})`; Mailpit va riavviato; il run e2e interrotto si rilancia. Nessun danno se si ricontrolla `git status` e l'ambiente prima di riprendere.
- La classe flaky e2e di epic 5 resta aperta e ROMPE ~4-6 test nei run paralleli (flight specs race form-refresh + people-management sotto carico): non ri-diagnosticarla ogni volta — procedura: DB fresco, re-run in isolamento delle spec estranee, `flights.spec:210` è l'unico che riproduce anche da solo (noto da epic 5). Follow-up consigliato invariato: test-hardening dedicato (attendere il segnale di submit-complete, DB per worker).

## Key Decisions (oltre a PRD/spine/CLAUDE.md e story files)

- **Stato scadenza MAI persistito**: derivato da `expiresAt` vs `todayDateOnlyUtc()` (`ok` >60gg / `expiring` ≤60 incluso il giorno stesso / `expired` < oggi); il filtro dashboard traduce lo stato in range di date SQL con lo STESSO `today` — filtro e badge non possono divergere.
- **Una scadenza corrente per (persona, tipo)**; rinnovo = update (lo storico visibile è quello delle proposte). Proposta = entità separata, una sola PENDING per expiry (partial unique index SQL a mano — il DSL Prisma non lo esprime; drift di `migrate diff` accettato e documentato).
- **Idempotenza alert = vincolo DB (AD-9)**: `SentAlert` unique (expiryId, threshold); insert-PRIMA-send (un crash tra insert e send perde quell'email — accettato, il digest staff è la rete); soglie = cadenza con catch-up, mai la soglia nel testo; **wipe-on-renewal**: `expiresAt` che cambia cancella i `SentAlert` in-tx, altrimenti il nuovo ciclo non allerterebbe mai.
- **Job route = unica route non-sessione** oltre alle auth: bearer timing-safe al boundary, service senza `Actor` (eccezione AD-5 documentata), entry esatta in `PUBLIC_API_PATHS` del middleware (ogni futura `/api/v1/jobs/*` ne richiede una).
- **Permessi epic 6**: lettura catalogo/dashboard = `expiries.manage` (admin+staff); scrittura catalogo = `settings.manage`; il titolare propone con `expiries.propose.own` (INSTRUCTOR/PILOT/STUDENT, NON staff) e legge le proprie con `self.read`; home widget solo per self-service (mai staff — asimmetria deliberata dei tile home).
- **Due sezioni paginate su una pagina** = due query param distinti (`page`, `dashboardPage`) E href che si preservano a vicenda (un query-object di Next `Link` SOSTITUISCE l'intera query string — lezione 6.4 M1).
