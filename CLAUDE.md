# AirManager — Gestionale per aviosuperficie

Software di gestione per un'aviosuperficie: piloti, velivoli, voli, PPR, finanze (piloti e aviosuperficie), scuola volo (allievi/istruttori), tariffe orarie, prenotazioni, scadenze (visite mediche, ratings), ruoli/permessi, export Excel/PDF.

## Stack (deciso con l'utente)

- Next.js 16 (App Router, TypeScript) — API-first: le API REST (Zod + OpenAPI) saranno consumate anche da una futura app mobile Flutter
- Prisma ORM + PostgreSQL 16
- Auth.js (NextAuth v5) con RBAC — ruoli: admin, istruttore, pilota, allievo (STAFF eliminato con la story 14.9: ADMIN è l'unica figura amministrativa)
- next-intl — UI in italiano + inglese
- **UI primaria e UNICA: design system "AirOps" custom** (epic 12-13) — `src/styles/airops.css` (token + mini-reset esplicito) + primitive React in `src/components/ui/` (`Badge`, `KPI`, `SlideOver`, `CalendarPopover`, ...), porting del prototipo in `docs/design-reference/airops/`; font self-hosted via `@fontsource/*` (Inter Tight/JetBrains Mono/Instrument Serif — regola: niente font fetch a build-time). Lo stack UI legacy è stato RITIRATO per intero (epic 12 story 12.1: shadcn/Radix/CVA; epic 13 story 13.11: Tailwind CSS, Geist, TanStack Table + componenti/glife orfani) — **nessuna pagina, componente o dipendenza legacy residua in `package.json`**.
- Test: Vitest + Playwright e2e

## Convenzioni

- **Route map**: la sidebar (`/dashboard/{overview,bookings,ppr,movements,pilots,instructors,fleet,expiries,logbook,my-account,my-compensation,billing,reports,settings}`) è interamente definita in `src/components/shell/route-registry.ts` (`NAV_ITEMS`, unica fonte di verità: href/icona/gruppo/ruoli visibili) — consultarlo invece di enumerare le route qui. Fuori registry: `/(auth)/{login,set-password,forgot-password}`, `/ppr` (modulo pubblico PPR), `people/{id}` (scheda persona AirOps — story 13.3, con estratto conto come sezione; linkata da Piloti/PilotLanding/billing, non dalla sidebar). `people/{id}/account` è un redirect verso `people/{id}` (deep-link retrocompatibile, story 13.3 R-13.3-b) — non una pagina propria.
- Branch: `main` + `dev` (v. modello branch sopra). Lo stato corrente branch/PR è per-sessione e vive SOLO in `docs/handoffs/HANDOFF.md` — mai registrarlo qui.
- Codice, commenti e identificatori in inglese; UI bilingue IT/EN via next-intl; documenti BMAD in italiano.
- Prima di ogni commit di una story: `npm run gates` deve passare (lint + typecheck + vitest + build in output compatto — stampa solo i fallimenti; MAI eseguire i 4 comandi verbosi separatamente nei gate).
- **Suite e2e: SEMPRE `scripts/e2e.sh`, MAI `playwright test` in foreground** (regola nata il 2026-07-30, epic 15). Il run completo su build di produzione supera il tetto di durata di un comando d'agent: chi lo lancia inline perde il risultato in un timeout, non sa distinguere un run morto da uno lento, e **rilancia da capo ripagando la build**. `scripts/e2e.sh start [args]` distacca il run con `setsid` (sopravvive alla sessione dell'agent che l'ha lanciato — il background della propria shell NO), tiene un lock (un secondo `start` RIPORTA il run in corso invece di duplicarlo: due suite sullo stesso DB e sulla stessa porta si corrompono le fixture a vicenda) e chiude il log con la sentinella `E2E_EXIT=<code>`. `scripts/e2e.sh status [n]` è l'UNICO modo di sapere com'è andata: **mai rieseguire la suite per scoprirlo**. Assenza di sentinella + nessun processo vivo = run MORTO, non run riuscito.
- **Build una volta per ciclo, non una per run**: sotto `CI=1` la build di produzione sta DENTRO il cronometro della suite (`playwright.config.ts#webServer.command`), quindi una serie di run la ripaga ogni volta, e un server già in ascolto su :3000 fa fallire il run invece di essere riusato. Per una serie: `env -u NODE_ENV npm run build && npm run start &` una volta, poi `E2E_REUSE_SERVER=1 scripts/e2e.sh start ...` per ogni run. La CI non setta mai quella variabile e continua a costruire da zero.
- **Unit test e validazione eager dell'env** (3 occorrenze: fix `3c6add9`, review 14.7 F1): un import nuovo verso un service che tocca `@/server/adapters/mail` o `@/server/crypto/*` trascina `@/lib/env` (validazione Zod EAGER all'import) dentro il test → `npm run gates` FALLISCE in una shell senza `.env` esportato, mentre CI resta verde (esporta env fittizie). Ogni test che importa un service "grosso" deve mockare la catena (`vi.mock('@/server/adapters/mail')` / `'./app-settings.service'` / `'@/lib/env'`, v. `bookings.service.test.ts`). Verifica: `env -u DATABASE_URL -u AUTH_SECRET npx vitest run <file>`.
- I test nuovi entrano in CI da soli (glob: vitest `src/**/*.test.ts`, Playwright `e2e/`) — MAI elencare test in CI. Se una story introduce una env var, un servizio o uno step di setup, aggiornare NELLO STESSO commit `.env.example`, `.github/workflows/ci.yml` e gli hook/script (`.claude/hooks/session-start.sh`, `scripts/`): il test `src/lib/env.ci-sync.test.ts` fallisce se l'env contract e la CI divergono.
- **e2e, `Escape` e i pannelli**: `SlideOver` chiude l'INTERO pannello su Escape (listener globale, `slide-over.tsx:29-31`) — MAI usarlo in un test per chiudere il popup di un `SearchCombobox`/picker: le asserzioni successive corrono contro l'animazione di chiusura e passano su nodi fantasma (review 14.3 F1/F2, 3 fallimenti deterministici mascherati). Chiudere il popup interagendo col campo successivo.
- **Ripetere run e2e mirati sullo stesso DB fa scattare il lock anti-brute-force** (TD-6: cap per identifier): dopo ~10 login lo stesso spec fallisce SEMPRE alla riga di login, identico alla flake nota ma deterministico. Prima di attribuirlo alla flake: `SELECT identifier, count(*) FROM "LoginAttempt" WHERE "createdAt" > now() - interval '15 minutes' GROUP BY 1` — se il conteggio è alto, resettare il DB.
- e2e: i click di navigazione usano selettori scoped al landmark (`getByRole('navigation', { name: 'Aree operative' })`) o `exact: true` — MAI un `getByRole('link', { name: ... })` page-level: il name-match di Playwright è substring, ogni nuovo link che contiene il label rompe il test (lezione 103-F1, epic 10). Stessa classe: MAI `hasText` con valori H:MM o date per disambiguare righe ("11:00" contiene "1:00") — regex `\b`-anchored o assert esatti sulla cella (lezione 11.2, epic 11); anche i NOMI delle fixture contano (una persona "Finestra" rompe `getByLabel('Fine')` via accessible-name del select — lezione 12.11 F2).
- **e2e, testid dell'albero mobile** (convenzione fissata dalla story 15.1, vale per tutto l'epic 15): i testid dell'albero DESKTOP non cambiano mai; una superficie mobile che DUPLICA una desktop prende lo stesso nome col suffisso `-mobile` (`logout-button-mobile`, `locale-switch-mobile`), una che esiste SOLO su mobile prende un nome nuovo con prefisso `mobile-` (`mobile-tab-bar`, `mobile-tab-<navItemId>`, `mobile-more-sheet`, `mobile-profile-menu`) — così lo strict mode di Playwright non vede mai due match per lo stesso nome quando desktop e mobile coesistono nel DOM.
- e2e, stato globale: gli spec che SCRIVONO AppSettings globali (`settings.spec.ts`, `booking-window.spec.ts`, `treasury-settings.spec.ts`) vivono nella catena di project serializzati di `playwright.config.ts` (`dependencies`: girano DOPO la suite principale; run locale singolo con `--no-deps`). OGNI nuovo spec che muta settings globali deve entrare nella catena — con `fullyParallel` uno spec "verde da solo" può rompere le create concorrenti degli altri (422 `BOOKING_OUTSIDE_WINDOW`, lezione 12.11 F1). Stessa regola per i test che ASSERISCONO aggregati GLOBALI (saldi all-time, KPI di mese) con uguaglianza: sotto `fullyParallel` flakano per costruzione (review Billing-2 F4: flaky 2 run su 2) → project serializzato (`billing-global.spec.ts`) o delta-assert a finestra breve, mai fotografia+uguaglianza.
- **Ambiente** (i fatti seguenti valgono per il container remoto; su altre macchine — es. la Fedora locale dell'utente — fa fede `docs/handoffs/HANDOFF.md`): PostgreSQL 16 disponibile nel container (`/usr/lib/postgresql/16`); Docker disponibile. Il bootstrap ambiente (deps, .env, Postgres, migrazioni, Mailpit) è automatico via hook SessionStart (`.claude/hooks/session-start.sh`, idempotente — rieseguibile a mano con `AIRMANAGER_BOOTSTRAP_FORCE=1`).
- **Playwright MCP** (`.mcp.json`, server `playwright` = `@playwright/mcp` headless sul Chromium preinstallato `/opt/pw-browsers/chromium` — path del container remoto: dove non esiste, workaround sanzionato = script `@playwright/test` throwaway in /tmp, v. HANDOFF): usarlo per la verifica UI interattiva durante dev e review (navigare l'app reale, screenshot, driving dei form) — complementare agli e2e Playwright (`e2e/`), che restano il gate automatico.
